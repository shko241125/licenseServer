# 라이선스 발급 서버 사용자 매뉴얼

이 매뉴얼은 발급 서버를 **화면에서 쓰는 사람**을 위한 안내서입니다. 서버를 처음 보는 사람도 이 문서만 따라 하면 로그인부터 발급, 검증, 계정 관리까지 할 수 있게 썼습니다.

| 독자 | 먼저 읽을 곳 |
|---|---|
| 조회자(VIEWER): 발급 이력을 보고 고객 문의에 답하는 사람 | §1~§4, §6, §9 |
| 발급자(ISSUER): 계약에 따라 라이선스를 발급하는 사람 | 위 + §5 |
| 관리자(ADMIN): 서명 키와 계정을 관리하는 사람 | 전부, 특히 §7·§8 |

- 설치·업그레이드·백업처럼 **서버를 운영하는 일**은 이 문서에서 다루지 않습니다. [../README.md](../README.md)와 [배포 안내](../../docs/release/license-server.md)를 봅니다.
- 화면 문구와 동작은 발급 서버 1.8.0 기준입니다.

---

## 1. 이 서버가 하는 일

STT 제품은 인터넷이 없는 고객 현장(폐쇄망)에서 돌아갑니다. 그래서 라이선스 확인도 인터넷 없이 해야 합니다. 이 서버는 그 라이선스 파일(`license.lic`)을 만들어 주는 사내 전용 웹 서버입니다.

```
[발급 서버]  계약 정보 입력 → 사내 비밀키로 서명 → license.lic
     │
     └─ 반입 절차(USB 등)로 고객 현장에 전달
                                   │
                         [고객 현장의 STT 서버]
                         SDK에 들어 있는 공개키로 서명을 확인 → 통과하면 기동
```

**비유:** 라이선스 파일은 "도장 찍힌 계약서"입니다. 서버는 회사 도장(비밀키)으로 도장을 찍고, 현장의 STT는 도장 모양(공개키)을 알고 있어서 진짜인지 가려냅니다. 내용을 한 글자라도 고치면 도장이 맞지 않게 됩니다.
- 비유가 깨지는 곳: 종이 도장은 흉내 낼 수 있지만, 전자 서명은 비밀키 없이는 만들 수 없습니다.

### 1.1 꼭 알아야 할 세 가지
1. **발급한 라이선스는 취소할 수 없습니다.** 파일이 현장에 들어가면 회수할 방법이 없습니다. "무효 처리"는 사내 장부에 표시만 합니다(§6.4).
2. **유예 기간이 없습니다.** 시험·개발 라이선스는 종료 시각이 지나는 순간부터 STT가 기동되지 않습니다. 만료 전에 갱신본을 반입해야 합니다.
3. **서명 키가 "해제됨" 상태일 때만 발급할 수 있습니다.** 키 해제는 관리자만 합니다(§7).

### 1.2 용어
| 용어 | 뜻 |
|---|---|
| 라이선스 파일 (`license.lic`) | 서명된 JSON 텍스트 파일입니다. 메모장으로 열어 읽을 수 있지만, 고치면 무효가 됩니다 |
| 서명 키 | 라이선스에 서명하는 비밀키입니다. 디스크에는 암호로 잠근 **봉인 파일**로만 있습니다 |
| 봉인 / 해제 | 봉인(sealed)은 키가 잠긴 상태로, 발급할 수 없습니다. 해제(unsealed)는 관리자가 패스프레이즈로 키를 메모리에 올린 상태로, 발급할 수 있습니다 |
| 패스프레이즈 | 봉인 파일을 여는 긴 암호입니다. 계정 비밀번호와 다릅니다 |
| 공개키 · 지문 | 공개키는 SDK에 넣어 서명을 확인하는 키입니다. 지문은 공개키의 SHA-256 값으로, 키가 바꿔치기되지 않았는지 대조할 때 씁니다 |
| 라이선스 ID | 발급 건마다 붙는 32자리 16진수입니다. 고객 문의, 무효 처리, 갱신에서 그 건을 가리키는 유일한 번호입니다 |
| 사이트 ID | 고객 설치 장소의 이름입니다(예: `SEOUL-MAIN-DC`) |
| 채널 | 동시에 처리할 수 있는 STT 세션 수입니다(§5.3) |
| OTP | 휴대폰 앱이 30초마다 만드는 6자리 숫자입니다. 비밀번호와 함께 써서 본인을 확인합니다 |
| 감사 로그 | 누가 언제 무엇을 했는지 남기는 기록입니다. 고치거나 지우면 탐지됩니다 |

## 2. 역할과 권한

계정마다 역할이 하나 있습니다. 상위 역할은 하위 역할의 권한을 모두 가집니다(**관리자 > 발급자 > 조회자**).

| 할 수 있는 일 | 조회자 | 발급자 | 관리자 |
|---|:-:|:-:|:-:|
| 대시보드, 발급 이력, 라이선스 상세 보기 | ○ | ○ | ○ |
| `license.lic` 다운로드 | ○ | ○ | ○ |
| 라이선스 검증(고객이 보낸 파일 확인) | ○ | ○ | ○ |
| 서명 키 상태·공개키 보기, `public.key` 다운로드 | ○ | ○ | ○ |
| 내 비밀번호 변경 | ○ | ○ | ○ |
| 새 라이선스 발급, 갱신 발급 | | ○ | ○ |
| 서명 키 해제·봉인 | | | ○ |
| 무효 처리 | | | ○ |
| 감사 로그 보기·무결성 검사 | | | ○ |
| 계정 추가·비활성화·비밀번호 초기화·OTP 초기화 | | | ○ |

- 권한이 없는 메뉴는 왼쪽 메뉴에 나타나지 않습니다. 주소를 직접 입력하면 "권한이 없습니다"(403) 화면이 나옵니다.
- 모든 계정은 **개인 계정**입니다. 계정을 여럿이 같이 쓰지 않습니다. 감사 로그에 사람 단위로 남기기 위해서입니다.

## 3. 접속과 로그인

### 3.1 준비물
- 관리망에 연결된 PC와 브라우저(Chrome, Edge 등)
- 접속 주소: `https://<서버 IP>:8443` (주소는 관리자에게 받습니다)
- OTP 앱이 있는 휴대폰: Google Authenticator, Microsoft Authenticator 등 **시간 기반(TOTP)** 앱이면 됩니다
- 관리자에게 받은 **사용자명과 임시 비밀번호**

처음 접속할 때 브라우저가 "연결이 비공개로 설정되어 있지 않습니다" 같은 인증서 경고를 띄울 수 있습니다. 사내 인증서를 PC에 아직 등록하지 않아서 생기는 경고입니다. 임의로 "계속"을 누르지 말고 관리자에게 확인합니다.

### 3.2 처음 로그인하기 (3단계)

처음 로그인하거나 관리자가 비밀번호를 초기화한 뒤에는 아래 세 단계를 차례로 거칩니다. 화면 위의 점 3개가 지금 몇 번째 단계인지 보여 줍니다.

**① 임시 비밀번호로 로그인**
1. 로그인 화면에 사용자명과 임시 비밀번호를 넣고 **로그인**을 누릅니다.
2. 임시 비밀번호에는 기한이 있습니다. 관리자가 만든 뒤 **72시간**이 지나면 쓸 수 없고, "임시 비밀번호가 만료되었습니다"가 나옵니다. 이때는 관리자에게 다시 초기화해 달라고 요청합니다.

**② 비밀번호 변경**
1. "현재 비밀번호"에 임시 비밀번호를 넣습니다.
2. "새 비밀번호"와 "새 비밀번호 확인"에 같은 값을 넣고 **변경**을 누릅니다.

| 비밀번호 규칙 | 어기면 나오는 문구 |
|---|---|
| 12자 이상 128자 이하 | 비밀번호는 12~128자여야 합니다. |
| 사용자명을 포함하지 않음(대소문자 무시) | 비밀번호에 사용자명을 포함할 수 없습니다. |
| 서로 다른 문자 4종 이상 | 비밀번호에 서로 다른 문자를 4종 이상 사용하세요. |
| 최근 3개 비밀번호 재사용 금지 | 최근 3개 비밀번호는 다시 쓸 수 없습니다. |

- 비밀번호 관리 프로그램을 쓰거나, 서로 관련 없는 단어 서너 개를 이어 붙이면 길고 기억하기 쉬운 비밀번호가 됩니다.

**③ OTP 등록**
1. 휴대폰 OTP 앱에서 계정 추가 → **"키 직접 입력"**(설정 키 입력)을 고릅니다.
2. 화면의 **키**를 앱에 입력합니다. 키를 클릭하면 전체가 선택되므로 복사해 붙여 넣을 수도 있습니다. 계정 이름은 알아보기 쉽게 정합니다(예: `라이선스서버-hong`).
   - 종류는 "시간 기반, 6자리, 30초"입니다. 앱 대부분은 기본값이 이와 같습니다.
   - "otpauth URI 보기"를 펼치면 같은 정보가 URI 형태로 나옵니다. URI를 받는 앱이면 이것을 써도 됩니다.
3. 앱에 나타난 6자리를 "앱에 표시된 6자리"에 넣고 **등록**을 누릅니다.
4. 등록이 끝나면 바로 대시보드로 들어갑니다.

> **주의: 이 화면에서 15분 넘게 머물지 않습니다.** 아무 동작이 없으면 15분 뒤 세션이 끝나 로그인 화면으로 돌아갑니다. 다시 로그인하면 **새 키**가 나오므로, 앱에 먼저 넣은 항목은 지우고 새 키로 다시 등록합니다. 비밀번호 변경(②)은 이미 저장되었으니 **바꾼 비밀번호**로 로그인합니다.

> **OTP 키는 비밀번호와 같습니다.** 화면을 캡처해 메신저로 보내거나 문서에 적어 두지 않습니다.

### 3.3 평소 로그인 (2단계)
1. 사용자명과 비밀번호로 로그인합니다.
2. "2단계 인증" 화면에 OTP 앱의 6자리를 넣고 **확인**을 누릅니다.
   - 코드는 30초마다 바뀝니다. 앞뒤 30초까지는 받아 줍니다.
   - **같은 코드는 한 번만** 쓸 수 있습니다. 방금 쓴 코드를 다시 넣으면 틀린 것으로 처리되니, 다음 코드가 나올 때까지 기다립니다.
   - 로그인을 그만두려면 **취소**를 누릅니다.

### 3.4 로그아웃과 세션 시간
- 왼쪽 아래 **로그아웃**을 누릅니다. 공용 PC가 아니어도 자리를 비울 때는 로그아웃합니다.

| 시간 제한 | 값 | 넘기면 |
|---|---|---|
| 아무 동작 없음(유휴) | 15분 | 다음 클릭 때 로그인 화면으로 돌아갑니다(별도 안내 문구 없음) |
| 로그인 후 전체 시간(절대) | 8시간 | 작업 중이어도 로그인 화면으로 돌아가고 "세션이 만료되었습니다"가 나옵니다 |
| 계정당 동시 로그인 | 1개 | 다른 PC나 브라우저에서 로그인하면 먼저 로그인한 쪽이 끊기고, 그쪽에 "세션이 만료되었습니다"가 나옵니다 |

- 발급 폼을 채우다가 15분이 지나면 입력한 내용을 잃습니다. 긴 내용(경고 문구 등)은 따로 적어 두고 붙여 넣습니다.

### 3.5 잠금
| 상황 | 결과 | 풀리는 방법 |
|---|---|---|
| 비밀번호 5회 연속 틀림 | 계정 15분 잠금 | 15분 기다림, 또는 관리자가 비밀번호 초기화 |
| 한 PC(IP)에서 5분 동안 로그인 시도 20회 초과 | "오류 429" 화면. 그 IP의 로그인 시도 일시 차단 | 몇 분 기다림 |
| 2단계 인증에서 OTP 5회 틀림 | 로그인 단계를 끝내고 처음으로 돌아감(실패 1회로 셈) | 다시 로그인 |
| 본인 확인(§3.6)에서 비밀번호나 OTP 틀림 | 로그인 실패 1회로 셈 | 5회가 쌓이면 계정 잠금 |

- 로그인에 실패하면 원인과 관계없이 같은 문구("계정이 잠겼거나 정보가 올바르지 않을 수 있습니다")가 나옵니다. 계정이 있는지 없는지를 바깥에 알려 주지 않기 위해서입니다. 원인은 관리자가 계정 화면의 "잠금" 칸과 감사 로그로 확인할 수 있습니다.
- 잠금 중에 계속 시도해도 잠금 시간이 늘어나지 않습니다.

### 3.6 본인 확인(재인증)
키 해제, 무효 처리, 계정 관리처럼 위험한 작업은 실행 직전에 **비밀번호와 OTP를 한 번 더** 묻습니다. 화면에 "본인 확인" 칸이 있으면 지금 로그인한 본인의 비밀번호와 지금 앱에 나온 OTP를 넣습니다.
- "재인증에 실패했습니다"가 나오면 비밀번호가 틀렸거나, 로그인 때 쓴 것과 **같은 30초 구간의 OTP**를 다시 넣은 경우입니다. 다음 코드를 기다려 넣습니다.

### 3.7 비밀번호를 바꾸고 싶을 때
왼쪽 아래 사용자 이름 밑의 **비밀번호 변경**을 누릅니다. 규칙은 §3.2 ②와 같습니다. 비밀번호를 잊었으면 관리자에게 초기화를 요청합니다(§8.3).

## 4. 화면 구성

```
┌──────────────┬──────────────────────────────────────────┐
│ 라이선스 발급 서버 │  페이지 제목            [주요 버튼]        │
│              │  설명                                     │
│ 업무          │ ─────────────────────────────────────── │
│  대시보드      │                                          │
│  발급 (발급자) │           본문                            │
│  발급 이력     │                                          │
│  검증         │                                          │
│ 관리          │                                          │
│  서명 키      │                                          │
│  감사 로그(관리자)│                                         │
│  계정 (관리자) │                                          │
│ 서명 키 [봉인됨] │                                         │
│ 사용자명 · 역할  │                                         │
│ 비밀번호 변경 · 로그아웃                                    │
└──────────────┴──────────────────────────────────────────┘
```
- 왼쪽 메뉴 아래의 **서명 키 배지**는 지금 발급할 수 있는지 알려 줍니다: 해제됨(초록) = 발급 가능, 봉인됨(노랑) = 관리자 해제 필요, 키 없음(빨강) = 서버 설정 문제(관리자 문의).
- 시각은 **한국 시간(KST)**으로 보여 주고, 필요한 곳에는 UTC를 함께 적습니다. 라이선스 파일 안의 시각은 모두 UTC입니다(KST = UTC + 9시간).

### 4.1 상태 배지
| 배지 | 뜻 |
|---|---|
| 발급됨 (`ISSUED`) | 정상 발급된 건. 파일을 내려받을 수 있습니다 |
| 처리 중 (`PENDING`) | 서명이 진행 중이거나, 서명 도중 서버가 멈춰 끝나지 않은 건 |
| 실패 (`FAILED`) | 서명이나 서명 후 확인에 실패한 건. 파일이 없습니다. 상세 화면에 오류가 나옵니다 |
| 무효 (`VOID`) | 관리자가 장부에서 무효로 표시한 건 |
| 운영 / 시험(데모) / 개발 | 라이선스 유형(`production` / `trial` / `dev`) |
| 유효 / 시작 전 / 만료 | 검증 결과의 기간 판정 |

### 4.2 대시보드
| 영역 | 내용 |
|---|---|
| 서명 키 | 지금 키 상태와 공개키 지문 앞 16자리. 관리자에게는 봉인 상태일 때 "해제하기 →" 링크가 보입니다 |
| 30일 내 만료 | 앞으로 30일 안에 끝나는 발급 건 수 |
| 최근 발급 | 최근 생성한 10건 |
| 서버 시각 | 서버의 현재 시각(KST, UTC). PC 시계가 아니라 이 시각으로 판단합니다 |
| 30일 내 만료 예정 표 | 남은 일수가 7일 이하면 빨간 배지입니다. 발급자에게는 "갱신 발급" 버튼이 보입니다 |

- 만료 예정 표에는 **이미 갱신 발급한 원본은 나오지 않습니다.** 갱신본을 발급했는데 계속 보인다면, 갱신본이 "발급됨" 상태인지 확인합니다.
- 개발 라이선스가 총 개발기한의 마지막 발급이면 빨간 글씨로 "총 개발기한 … 도래 — 연장 계약 확인"이 붙습니다. 영업·계약 담당에게 기한 연장 여부를 확인할 때입니다.

## 5. 라이선스 발급 (발급자·관리자)

### 5.1 발급 전에 확인할 것
- [ ] 계약서나 요청서에 프로젝트명, 사이트 ID, 유형, 채널 수, 기간이 모두 있는가
- [ ] 같은 고객의 이전 발급 건이 있는가(있으면 새 발급이 아니라 **갱신 발급**, §5.6)
- [ ] 왼쪽 아래 서명 키 배지가 **해제됨**인가. 봉인 상태여도 입력과 미리보기는 할 수 있지만, 마지막 "발급" 버튼은 눌리지 않습니다. 관리자에게 해제를 요청합니다

### 5.2 발급 순서 한눈에
```
발급 메뉴 → ① 입력 → [미리보기] → ② 확인 → [발급] → 상세 화면 → [license.lic 다운로드] → 반입 절차로 전달
                         ↑            │
                         └──[수정]─────┘
```

### 5.3 ① 입력 화면 — 칸별 설명

**기본 정보** (모두 라이선스 파일에 그대로 기록되고, 고객도 읽을 수 있습니다)

| 칸 | 넣는 값 | 규칙 |
|---|---|---|
| 프로젝트명 | 계약상 프로젝트 이름. 예: `STT Platform Modernization` | 필수. 256바이트 이하(한글 약 85자). 줄바꿈·탭 불가. **사내 코드명은 넣지 않습니다** |
| 사이트 ID | 설치 장소 이름. 예: `SEOUL-MAIN-DC` | 필수. 256바이트 이하. 전에 쓴 값이 자동 완성됩니다. 같은 장소는 같은 값으로 씁니다(이력 검색 기준). 한글도 쓸 수 있지만, 다운로드 파일 이름에는 영문·숫자·`_`·`-`만 남습니다(§5.5) |
| 유형 | `production`(운영) · `trial`(시험·데모) · `dev`(개발) | 필수. 기간 규칙이 유형마다 다릅니다(아래) |
| 솔루션 | 제품 구분. 기본 `sonastt-universal` | 필수. 128바이트 이하 |

- 길이는 글자 수가 아니라 **UTF-8 바이트**로 셉니다. 영문·숫자는 1바이트, 한글은 3바이트입니다.

**채널** — 동시에 몇 개의 STT 세션을 쓸 수 있는지 정합니다.

| 칸 | 뜻 |
|---|---|
| total | **모든 항목을 합친 동시 세션의 최대 수.** 1~100000 |
| 항목 | 채널을 묶는 이름. 기본 행은 `offline`(파일 처리), `online`(실시간)입니다. 이름은 자유롭게 정할 수 있습니다 |
| 세부 항목 | 항목 안의 엔진 이름. 예: `sonastt`, `sonaml`, `sonaasr` |
| 상한 | 그 세부 항목의 동시 세션 최대 수. 0~total |

예: total 16, `offline.sonastt` 8, `online.sonastt` 8, `offline.sonaasr` 4라면, 각 엔진은 자기 상한까지 쓸 수 있고 **모두 합쳐서는 16을 넘을 수 없습니다.**

- 이름은 **소문자·숫자·`_`만**, 1~64자입니다. `total`은 항목 이름으로 쓸 수 없습니다.
- 이름을 비웠거나 상한이 0인 행은 파일에 넣지 않습니다. 쓰지 않는 기본 행은 상한을 비우거나 0으로 두면 됩니다.
- 상한이 1 이상인 세부 항목이 **하나 이상** 있어야 합니다.
- 같은 (항목, 세부 항목)을 두 번 넣을 수 없습니다. `offline.sonastt`와 `online.sonastt`는 서로 다른 행이라 괜찮습니다.
- 행이 모자라면 채울 수 있는 만큼 채우고 미리보기 → **수정**으로 돌아옵니다. 빈 행이 3개 늘어납니다.
- 항목·세부 항목 이름은 SDK가 읽는 이름과 같아야 동작합니다. 새 이름을 쓰기 전에 제품 담당에게 확인합니다.

**유효 기간 (KST)** — 날짜와 시각은 **한국 시간**으로 넣습니다. 파일에는 UTC로 바뀌어 들어갑니다.

| 유형 | 시작 | 종료 | 1회 최대 기간 | 총 개발기한 |
|---|---|---|---|---|
| 운영 `production` | 필수 | 입력해도 무시하고 **영구**(`9999-12-31T23:59:59Z`) | — | 쓰지 않음 |
| 시험 `trial` | 필수 | 필수 | **180일** | 쓰지 않음 |
| 개발 `dev` | 필수 | 필수 | **1년(366일)** | **필수**. 종료는 이 날짜 안이어야 함 |

- 시각을 비우면 시작은 그날 `00:00:00`, 종료는 기본값 `23:59:59`입니다.
- 새 발급 화면을 열면 시작은 오늘, 종료는 1년 뒤 전날로 채워져 있습니다. **시험(trial)으로 바꾸면 종료를 180일 안으로 줄여야** 합니다.
- **총 개발기한**은 개발 과제 전체 기간입니다(예: 3년 과제의 마지막 날). 라이선스 파일에는 들어가지 않고 사내 기록에만 남습니다. 개발 라이선스는 이 기한 안에서 1년씩 갱신 발급합니다. 날짜만 넣으며, 그날 23:59:59(KST)까지로 봅니다.
- 시험·개발에 9999년 종료일은 넣을 수 없습니다(영구 발급은 운영만).

**경고 문구** — 라이선스 파일에 들어가는 고지문입니다. 기본 문구가 채워져 있습니다. 4096바이트 이하이고 줄바꿈은 넣을 수 없습니다(한 문단으로 씁니다).

다 채웠으면 **미리보기**를 누릅니다. 규칙에 어긋난 칸이 있으면 그 칸 아래에 빨간 글씨로 이유가 나옵니다.

### 5.4 ② 확인(미리보기) 화면
1. 맨 위에 "발급한 라이선스는 취소할 수 없습니다"가 나옵니다. 아래 내용을 계약서와 **한 줄씩 대조**합니다.
2. **확인이 필요한 항목**(노란 상자)이 있으면 읽고 판단합니다. 오류가 아니라서 발급은 됩니다.

| 경고 | 뜻 |
|---|---|
| 시작 시각이 하루 이상 과거입니다. | 날짜를 잘못 넣지 않았는지 확인합니다. 소급 발급이 맞으면 그대로 진행합니다 |
| 종료 시각이 이미 지났습니다. 발급해도 즉시 만료 상태입니다. | 거의 항상 입력 실수입니다 |
| 세부 항목 상한의 합(N)이 total(M)보다 작아 total 까지 쓸 수 없습니다. | 세부 항목을 다 써도 total에 못 미칩니다. 의도한 것인지 확인합니다 |

3. "서명될 계약 JSON"을 펼치면 실제로 서명될 내용을 볼 수 있습니다. `license_id`는 "(발급 시 생성)"으로 보이며, 발급할 때 정해집니다.
4. 고칠 것이 있으면 **수정**을, 맞으면 **발급**을 누릅니다. 발급 버튼은 **한 번만** 누릅니다. 두 번 눌리거나 새로 고쳐도 한 건만 만들어집니다.

### 5.5 발급 후
1. 상세 화면으로 이동하고 "발급했습니다"가 나옵니다.
2. **license.lic 다운로드**를 누릅니다. 파일 이름은 `<사이트 ID>_<라이선스 ID>.lic`입니다.
   - 사이트 ID에서 영문·숫자·`_`·`-`가 아닌 문자(한글, 공백, `.`, 괄호 등)는 한 글자마다 `_`로 바뀝니다. 파일 이름이 어느 컴퓨터에서나 같게 보이고, 폐쇄망 리눅스 서버에서도 그대로 다룰 수 있게 하려는 규칙입니다.

     | 사이트 ID | 파일 이름 |
     |---|---|
     | `SEOUL-MAIN-DC` | `SEOUL-MAIN-DC_<라이선스 ID>.lic` |
     | `서울센터` | `_____<라이선스 ID>.lic` (한글 4자 → `_` 4개, 그 뒤 구분자 `_`) |
     | `부산 지점(2)` | `______2__<라이선스 ID>.lic` |

   - **이름이 밑줄로 보여도 정상입니다.** 바뀌는 것은 파일 이름뿐이고, 파일 **내용**의 사이트 ID는 입력한 한글 그대로 서명되어 있습니다. 파일을 메모장으로 열거나 검증 메뉴(§6.3)에 올리면 확인할 수 있습니다.
   - 어느 건인지는 이름 뒤쪽의 **라이선스 ID**로 구분합니다. 상세 화면 맨 위의 ID와 같습니다.
   - 사이트를 이름으로 알아보고 싶으면 사이트 ID를 영문으로 정해 씁니다(예: `SEOUL-MAIN-DC`). 이미 한글로 발급한 사이트는 이력 검색이 이어지도록 같은 값을 계속 씁니다.
   - 현장 STT 서버가 읽는 파일 이름이 정해져 있으면, 받는 쪽에서 그 이름(보통 `license.lic`)으로 바꿉니다. 이름을 바꿔도 서명에는 영향이 없습니다.
   - **파일을 열어 고치지 않습니다.** 공백 하나만 바뀌어도 현장에서 `1004`(서명 불일치)로 거부됩니다.
3. 상세 화면의 **파일 SHA-256**을 함께 전달하면, 받는 쪽이 `sha256sum` 결과와 비교해 전달 중 손상을 확인할 수 있습니다.
4. 반입 전에 이 서버의 **검증** 메뉴(§6.3)에 내려받은 파일을 다시 올려 `OK`인지 확인해 두면 안전합니다.
5. 오늘 발급을 모두 마쳤으면 관리자에게 알려 **지금 봉인**을 누르게 합니다(§7.3).

**발급이 실패했을 때**: 화면 위에 "발급 실패 (오류 이름): …"가 나오고, 이력에는 **실패** 건이 남습니다. 실패 건은 파일이 없으므로 고객에게 아무것도 나가지 않았습니다. 같은 내용으로 다시 발급하고, 계속 실패하면 오류 문구를 관리자에게 전달합니다.

### 5.6 갱신 발급
기간이 끝나 가는 시험·개발 라이선스를 이어 주거나, 채널 수를 바꿔 새로 발급할 때 씁니다. 원본 내용을 그대로 채워 주므로 입력 실수가 줄어듭니다.

1. 원본의 상세 화면에서 **이 건으로 갱신 발급**을 누릅니다(대시보드 만료 예정 표의 **갱신 발급**도 같습니다).
2. 다음 값이 자동으로 채워집니다.

| 칸 | 채워지는 값 |
|---|---|
| 프로젝트·사이트·유형·솔루션·채널·경고 문구 | 원본과 같음 |
| 시작 | 시험·개발: **원본 종료 다음 날**. 운영(영구): **오늘** |
| 종료 | 시험: 시작 + 180일 범위의 마지막 날. 개발: 시작 + 1년 전날(총 개발기한이 먼저 오면 그 날) |
| 총 개발기한 | 개발이면 원본 값 |

3. 바뀐 계약 내용(채널 수 등)만 고치고 미리보기 → 발급합니다.
4. 갱신본은 원본과 **다른 라이선스 ID**를 받고, 상세 화면의 "원본"에 원본 ID가 링크됩니다.

- 과제 기한이 연장됐으면 갱신 폼에서 **총 개발기한**을 새 날짜로 고칩니다. 고치지 않으면 "발급 종료가 총 개발기한을 넘습니다"가 나옵니다.
- 갱신본을 발급해도 원본 파일은 현장에서 자기 종료일까지 계속 유효합니다. 오프라인이라 원본을 끌 방법이 없습니다.
- 현장에서는 새 파일로 교체한 뒤 **STT 서버를 재시작**해야 새 라이선스가 적용됩니다.

### 5.7 자주 하는 실수
| 실수 | 결과 | 예방 |
|---|---|---|
| 기간을 UTC로 착각해 입력 | 9시간 어긋남 | 화면 입력은 항상 KST입니다 |
| 시험인데 종료를 1년으로 둠 | "시험(trial)은 1회 180일 이내로…" 오류 | 유형을 먼저 고르고 종료를 고칩니다 |
| 같은 사이트를 다른 철자로 입력(`SEOUL-DC`, `Seoul-DC`) | 이력 검색과 만료 관리가 흩어짐 | 자동 완성 목록에서 고릅니다 |
| 받은 파일을 메모장으로 열어 저장 | 줄바꿈·인코딩이 바뀌어 현장 거부 | 파일은 열지 않고 그대로 전달합니다 |
| 만료 직전에 갱신 | 반입이 늦으면 현장 중단 | 대시보드를 매주 확인합니다(유예 기간 없음) |

## 6. 조회와 고객 문의 대응 (모든 역할)

### 6.1 발급 이력
- **발급 이력** 메뉴에서 모든 건을 생성 시각 역순으로 봅니다. 한 쪽에 50건씩 나오고, 아래 "다음 →"으로 넘깁니다.
- 검색칸에 프로젝트명·사이트 ID·라이선스 ID를 넣고, 상태(발급됨·처리 중·실패·무효)로 걸러 **검색**합니다. 일부만 넣어도 찾고, 대소문자는 가리지 않습니다(예: `seoul`). **초기화**는 조건을 지웁니다.

### 6.2 라이선스 상세
| 영역 | 내용 |
|---|---|
| 계약 정보 | 프로젝트, 사이트, 유형, 솔루션, 채널, 시작·종료(KST와 UTC), 총 개발기한(개발) |
| 발급 정보 | 상태, 발급 시각·발급자, 원본(갱신본이면), 라이선스 ID, 서명 키 지문, 파일 SHA-256 |
| 파일 내용 | `license.lic` 원문 |
| 무효 처리 | 관리자에게만 보입니다(§6.4) |

- 다운로드는 감사 로그에 `DOWNLOAD`로 남습니다.

### 6.3 라이선스 검증 — "이 파일 진짜인가요?"
고객이나 현장 엔지니어가 파일을 보내 오면, 이 서버의 키로 서명된 파일인지와 지금 유효한지를 확인합니다.

1. **검증** 메뉴에서 파일을 고르거나, 내용을 텍스트 칸에 붙여 넣습니다. 둘 다 넣으면 파일이 우선합니다.
2. **검증**을 누릅니다.
3. 결과를 읽습니다.

| 결과 | 뜻 | 할 일 |
|---|---|---|
| `OK` · 유효 | 이 서버가 서명했고 바뀌지 않았으며, 지금 기간 안 | 문제는 라이선스가 아닙니다. 현장의 다른 원인(시계, 파일 경로 등)을 봅니다 |
| `OK` · 시작 전 | 진짜이지만 아직 시작 전 | 시작 시각을 안내하거나, 현장 서버 시계를 확인 |
| `OK` · 만료 | 진짜이지만 기간이 끝남 | 갱신 발급 |
| `LICENSE_BAD_SIGNATURE` | 내용이 고쳐졌거나 다른 키로 서명됨 | 이력에서 라이선스 ID로 원본을 찾아 다시 내려받아 전달 |
| `LICENSE_PARSE_ERROR` | JSON이 아님(다른 파일, 옛 `.key` 형식, 깨진 파일) | 올바른 파일을 다시 받음 |
| `LICENSE_INVALID_FIELD`, `LICENSE_UNSUPPORTED_VERSION` | 형식이 규격에 맞지 않음 | 관리자에게 전달 |

- 결과가 `OK`면 파일에 적힌 값(라이선스 ID, 프로젝트, 기간, 채널 등)이 함께 나옵니다. 라이선스 ID로 이력을 찾아 **무효 처리된 건이 아닌지** 확인합니다.
- `check_mode`는 검증기가 **실제로 적용한** 판정 수준입니다. 지금 발급하는 파일(`license_ver` 1)은 발급 유형(운영·시험·개발)과 관계없이 항상 `full`입니다.
  - 내려받은 `.lic` 파일을 열어 보면 `check_mode` 키가 없습니다. 정상입니다. 키가 없으면 `full`로 판정하도록 정해져 있습니다.
  - 상세 화면에는 이 값이 나오지 않습니다. 파일에 없는 값이라 장부에도 저장하지 않으며, 검증 화면에서만 확인합니다.
  - 발급 화면에는 `check_mode`를 고르는 칸이 없습니다. 형식 판이 2 이상으로 올라갈 때 서버가 정해진 규칙으로 넣으며, 사람이 직접 고르지 않습니다.
- 검증한 사실은 감사 로그에 `VERIFY`로 남습니다.

### 6.4 무효 처리 (관리자)
계약 해지, 잘못 발급한 건 등을 **사내 장부에서** 무효로 표시합니다.

1. 상세 화면 아래 **무효 처리**에 사유(500자 이하)를 넣습니다.
2. 본인 확인(비밀번호 + OTP)을 넣고 **무효 처리**를 누릅니다.

- **현장 파일은 계속 동작합니다.** 오프라인 구조라 이미 반입된 파일을 끌 방법이 없습니다. 실제로 쓰지 못하게 하려면 현장에서 파일을 회수·삭제하는 절차가 따로 필요합니다.
- "발급됨" 상태인 건만 무효로 할 수 있고, 되돌릴 수 없습니다. 무효 건은 만료 알림에서 빠집니다.

## 7. 서명 키 관리 (관리자)

### 7.1 키 상태
**서명 키** 메뉴에서 봅니다(모든 역할이 볼 수 있고, 해제·봉인은 관리자만 합니다).

| 상태 | 뜻 | 발급 |
|---|---|---|
| 봉인됨 `SEALED` | 키가 봉인 파일 안에 잠겨 있음. 서버를 켠 직후는 항상 이 상태 | 불가 |
| 해제됨 `UNSEALED` | 키가 메모리에 올라와 있음 | 가능 |
| 키 없음 `MISSING` | 봉인 파일이 없거나, 설치 때 고정한 지문과 다름(바꿔치기 의심) | 불가. 서버 운영 담당에게 즉시 알림 |

- 화면에는 해제 시각, 해제 시도 잠금(있으면), 오류, **공개키**와 **공개키 지문**이 나옵니다.

### 7.2 키 해제 (발급 전에)
1. **서명 키** 메뉴의 "키 해제 (unseal)"에 **봉인 패스프레이즈**를 넣습니다. 계정 비밀번호가 아니라, 키를 만들 때 정한 20자 이상의 별도 암호입니다.
2. 본인 확인(비밀번호 + OTP)을 넣고 **해제**를 누릅니다.

| 결과 문구 | 뜻 |
|---|---|
| 서명 키를 해제했습니다. … | 성공. 발급자가 발급할 수 있습니다 |
| 패스프레이즈가 올바르지 않습니다. | 패스프레이즈 오타 |
| 실패가 반복되어 잠시 잠겼습니다. … | 패스프레이즈 5회 오류 → **15분** 동안 해제 불가 |
| 봉인 파일의 비밀키와 공개키가 짝이 맞지 않습니다. … | 봉인 파일 손상·조작 의심. 서버 운영 담당에게 알림 |
| 봉인 키 파일이 없습니다. | 서버 설정 문제 |
| 재인증에 실패했습니다. | 비밀번호나 OTP가 틀림(§3.6) |

- 패스프레이즈는 보통 두 사람이 나눠 보관합니다. 두 사람이 함께 있을 때 해제합니다.

### 7.3 봉인
- 발급을 마치면 **지금 봉인**을 누릅니다. 본인 확인 없이 바로 봉인됩니다.
- 누르지 않아도 **마지막 발급 뒤 8시간** 동안 발급이 없으면 서버가 자동으로 봉인합니다(1분 간격으로 확인). 이 시간은 로그인 세션과 따로 셉니다. 로그아웃해도 키는 해제된 채로 남으니, 자동 봉인에 기대지 말고 직접 봉인합니다.
- 서버를 재시작하면 키는 항상 봉인 상태로 돌아갑니다.

### 7.4 공개키 전달 (SDK 빌드 담당에게)
SDK는 빌드할 때 공개키를 넣습니다. 처음 한 번, 그리고 키를 바꿨을 때만 전달합니다.
1. **public.key 다운로드 (SDK 빌드용)** 버튼으로 파일을 받아 SDK 빌드 담당에게 보냅니다.
2. 화면의 **공개키 지문(SHA-256)**은 **다른 경로**(사내 문서, 구두 확인 등)로 알려 줍니다. 받는 쪽은 `base64 -d public.key | sha256sum` 결과와 대조합니다.
   - 공개키는 비밀이 아니지만, 전달 중에 **바꿔치기**되면 다른 사람이 라이선스를 만들 수 있게 됩니다. 그래서 파일과 지문을 서로 다른 길로 보냅니다.

## 8. 계정 관리 (관리자)

**계정** 메뉴에서 합니다. 모든 변경에 본인 확인(비밀번호 + OTP)이 필요합니다.

### 8.1 계정 목록 읽기
| 칸 | 내용 |
|---|---|
| 사용자 · 역할 | 사용자명과 관리자·발급자·조회자 |
| 상태 | 활성/비활성. 아래에 임시 비밀번호 상태("임시 비밀번호 ~ 만료 시각", "만료됨 → 초기화 필요", 초기 관리자는 "만료 없음") |
| OTP | 등록/미등록 |
| 잠금 | 잠겨 있으면 풀리는 시각 |
| 작업 | **관리**를 펼치면 비활성화·비밀번호 초기화·OTP 초기화가 나옵니다 |

### 8.2 계정 추가
1. 화면 아래 "계정 추가"에 사용자명, 역할, 임시 비밀번호를 넣습니다.
   - 사용자명: 소문자·숫자·`.`·`_`·`-` 3~32자. 사람을 알아볼 수 있게 정합니다(예: `hong.gildong`).
   - 역할: 하는 일에 필요한 **가장 낮은 역할**을 줍니다. 고객 문의만 받으면 조회자, 발급하면 발급자입니다. 관리자는 최소 인원으로 둡니다.
   - 임시 비밀번호: 비밀번호 규칙(§3.2 ②)을 따릅니다.
2. 본인 확인을 넣고 **추가**를 누릅니다. "(사용자명) 계정을 만들었습니다. 임시 비밀번호는 (시각) 까지 유효하며, …"가 나옵니다.
3. 사용자명과 임시 비밀번호를 **따로따로** 전달합니다(예: 사용자명은 메일, 비밀번호는 구두). 사용자는 72시간 안에 첫 로그인(§3.2)을 마쳐야 합니다.

> 임시 비밀번호를 아는 사람은 누구든 먼저 로그인해 **자기 휴대폰에 OTP를 등록**할 수 있습니다. 임시 비밀번호는 본인에게만 전달하고, 첫 로그인을 미루지 않게 합니다.

### 8.3 비밀번호 초기화
비밀번호를 잊었거나, 임시 비밀번호가 만료됐거나, 계정이 잠겼을 때 씁니다.
1. 그 계정의 **관리** → "비밀번호 초기화"에 새 임시 비밀번호를 넣고 본인 확인 후 실행합니다.
2. 그 사용자의 **로그인 중인 세션은 즉시 끝나고**, 잠금도 풀립니다. 다음 로그인 때 비밀번호를 바꿔야 하며, 새 임시 비밀번호도 72시간 뒤 만료됩니다.
3. OTP는 그대로입니다. 사용자는 기존 OTP 앱으로 로그인합니다.

### 8.4 OTP 초기화
휴대폰을 바꿨거나 잃어버려 OTP를 쓸 수 없을 때 씁니다.
1. 그 계정의 **관리** → "OTP 초기화"에서 본인 확인 후 실행합니다.
2. 그 사용자의 세션이 즉시 끝나고, 다음 로그인 때 OTP를 새로 등록합니다(§3.2 ③). 비밀번호는 그대로입니다.
3. 휴대폰을 **잃어버린** 경우에는 비밀번호도 함께 초기화하는 편이 안전합니다.

### 8.5 비활성화·활성화
퇴사, 휴직, 역할 변경 등으로 더 이상 쓰지 않는 계정은 **비활성화**합니다.
- 비활성화하면 그 사용자의 세션이 즉시 끝나고 로그인할 수 없습니다. 계정과 기록은 남습니다(삭제 기능은 없습니다).
- **자기 계정**과 **마지막 관리자 계정**은 비활성화할 수 없습니다.
- 역할을 바꾸는 기능은 없습니다. 새 역할로 계정을 새로 만들고, 기존 계정을 비활성화합니다.

### 8.6 초기 관리자 계정 `admin`
- 서버를 설치하면 `admin` 계정 하나가 만들어집니다. 초기 비밀번호는 설치 담당이 서버의 비밀값 파일에서 확인해 알려 줍니다. 이 비밀번호에는 만료가 없으므로 **설치 직후 바로 첫 로그인을 마칩니다.**
- 이후 관리자마다 개인 계정을 만들고, 공용 `admin`은 비상용으로만 둡니다.
- 관리자가 한 명뿐인데 그 비밀번호와 OTP를 모두 잃으면, 서버를 처음 상태로 되돌리는 방법밖에 없습니다(모든 기록이 사라짐). **관리자 계정을 최소 두 개** 둡니다.

## 9. 감사 로그 (관리자)

### 9.1 보기
- **감사 로그** 메뉴에 최근 300건이 최신순으로 나옵니다.
- 행위 코드 칸에 코드를 정확히 넣고(예: `ISSUE`) **필터**를 누르면 그 행위만 봅니다.

| 행위 코드 | 뜻 |
|---|---|
| `LOGIN_PASSWORD_OK` / `LOGIN_OK` | 비밀번호 통과 / OTP까지 통과해 로그인 완료 |
| `LOGIN_FAIL` / `MFA_FAIL` / `ACCOUNT_LOCKED` | 비밀번호 실패 / OTP 실패 / 5회 실패로 잠금 |
| `PASSWORD_CHANGE` / `PASSWORD_CHANGE_DENIED` / `TOTP_ENROLL` | 비밀번호 변경 / 변경 거부(규칙 위반 등) / OTP 등록 |
| `UNSEAL` / `UNSEAL_FAIL` / `UNSEAL_LOCKED` / `SEAL` | 키 해제 / 해제 실패 / 해제 잠금 / 봉인(`manual` 또는 자동 `idle for …`) |
| `ISSUE` / `ISSUE_FAILED` / `DOWNLOAD` / `VERIFY` / `VOID` | 발급 / 발급 실패 / 다운로드 / 검증 / 무효 처리 |
| `USER_BOOTSTRAP` / `USER_CREATE` / `USER_ENABLE` / `USER_DISABLE` / `USER_RESET_PASSWORD` / `USER_RESET_TOTP` | 초기 관리자 생성 / 계정 추가 / 활성화 / 비활성화 / 비밀번호 초기화 / OTP 초기화 |
| `AUDIT_VERIFY` | 해시 체인 무결성 검사 실행 |

### 9.2 무결성 검사 (주 1회 권장)
감사 로그의 각 행은 앞 행의 해시를 이어 받는 **해시 체인**으로 묶여 있습니다. 누군가 DB에서 기록을 고치거나 지우면 사슬이 끊깁니다.

**비유:** 페이지마다 앞 페이지의 지문을 적어 둔 장부입니다. 중간 한 장을 고치면 다음 장에 적힌 지문과 맞지 않아 바로 드러납니다.
- 비유가 깨지는 곳: 맨 끝 몇 장을 통째로 찢어 내면 장부 안에서는 티가 나지 않습니다. 그래서 마지막 해시를 장부 밖(백업 앵커)에도 적어 둡니다.

1. **해시 체인 무결성 검사**를 누릅니다.
2. "정상 — N건 검사, 마지막 해시 …"면 정상입니다. 마지막 해시를 백업 앵커 기록과 비교하는 방법은 [감사 해시 체인 방법론](audit-hash-chain.md)에 있습니다.
3. "변조 탐지 — seq N — 사유"가 나오면 **즉시 보안 담당과 서버 운영 담당에게 알립니다.** 서버를 재시작하거나 기록을 건드리지 않습니다.

## 10. 문제 해결

| 증상 | 원인 | 조치 |
|---|---|---|
| "로그인에 실패했습니다. 계정이 잠겼거나…" | 비밀번호 오류 또는 잠금(15분) | 잠시 뒤 다시 시도. 계속되면 관리자에게 비밀번호 초기화 요청 |
| "임시 비밀번호가 만료되었습니다." | 임시 비밀번호 72시간 경과 | 관리자에게 비밀번호 초기화 요청 |
| 작업 중 갑자기 로그인 화면이 나옴 | 15분 무동작(안내 문구 없음). "세션이 만료되었습니다."가 함께 나오면 8시간 경과 또는 다른 곳에서 같은 계정으로 로그인 | 다시 로그인. 내가 다른 곳에서 로그인하지 않았는데 끊겼다면 관리자에게 알림 |
| "인증 코드가 올바르지 않습니다." | OTP 오타, 휴대폰 시각이 틀림, 같은 코드 재사용 | 다음 코드를 기다려 입력. 휴대폰 시간을 "자동 설정"으로 |
| OTP 등록 중 로그인 화면으로 돌아감 | 등록 화면에서 15분 경과 | 앱의 이전 항목을 지우고, 바꾼 비밀번호로 로그인해 새 키로 등록 |
| 휴대폰 교체·분실로 OTP를 못 씀 | — | 관리자에게 OTP 초기화 요청(§8.4) |
| "권한이 없습니다"(403) | 역할에 없는 작업, 또는 로그인 단계(비밀번호 변경·OTP)가 끝나지 않음 | 역할 확인. 로그인 단계를 마치고 다시 시도 |
| 발급 버튼이 회색 / "서명 키가 봉인 상태라 발급할 수 없습니다." | 키 봉인 상태 | 관리자에게 키 해제 요청(§7.2) |
| "입력값을 확인하세요: …" | 입력 규칙 위반 | 문구에 나온 칸을 고침(§5.3) |
| 발급했는데 상태가 "처리 중"으로 남음 | 서명 도중 서버가 멈춤 | 파일이 없으므로 고객에게 나간 것은 없음. 다시 발급하고 관리자에게 알림 |
| 현장에서 `1004`(서명 불일치) | 파일이 바뀌었거나 다른 키로 빌드한 SDK | 검증 메뉴(§6.3)로 파일 확인. `OK`면 현장 SDK의 공개키 문제 |
| 현장에서 `1008`(만료) | 시험·개발 라이선스 종료 | 갱신 발급(§5.6). 유예 기간 없음 |
| 현장에서 `1007`(시작 전) | 시작 시각 전이거나 현장 서버 시계가 틀림 | 시작 시각과 현장 시계 확인 |
| 내려받은 파일 이름이 `_____…lic`처럼 밑줄로 깨져 보임 | 사이트 ID가 한글 등이라 파일 이름에서 `_`로 바뀜(인코딩 오류 아님) | 정상입니다. 라이선스 ID로 구분하고, 필요하면 이름을 바꿉니다(§5.5). 이름을 바꿔도 서명에는 영향 없음 |
| 브라우저 인증서 경고 | 사내 인증서 미등록 | 관리자에게 문의 |
| "요청을 처리하지 못했습니다"(오류 429) | 한 PC에서 로그인을 너무 자주 시도함 | 몇 분 뒤 다시 시도 |
| "요청을 처리하지 못했습니다"(그 밖의 번호) | 일시적 서버 오류 | 잠시 뒤 다시 시도, 계속되면 관리자에게 오류 번호·시각과 함께 알림 |

현장 오류 코드 전체와 조치는 [현장 운영 안내](../../docs/sdk/06-field-operations.md)에 있습니다.

## 12. 자주 묻는 질문

**Q. 잘못 발급했습니다. 취소할 수 있나요?**
아니요. 파일이 아직 나가지 않았다면 전달하지 않고, 관리자가 무효 처리해 장부에 표시합니다. 올바른 내용으로 새로 발급합니다. 이미 나갔다면 현장에서 파일을 교체·삭제하는 절차가 필요합니다.

**Q. 운영 라이선스는 언제 만료되나요?**
만료되지 않습니다. 종료가 `9999-12-31T23:59:59Z`(영구)로 고정됩니다. 채널 수 변경 등 계약이 바뀌면 갱신 발급으로 새 파일을 만듭니다.

**Q. 같은 고객에게 채널을 늘려 주려면?**
기존 건에서 **갱신 발급**하고 채널만 고칩니다. 현장은 새 파일로 교체한 뒤 STT 서버를 재시작합니다.

**Q. 현장 엔지니어가 "라이선스가 안 된다"고 합니다.**
현장 오류 코드(1001~1011)를 먼저 받습니다. 파일을 받아 검증 메뉴에 올려 보면 파일 문제인지 현장 문제인지 바로 갈립니다(§6.3).

**Q. 조회자도 라이선스 파일을 내려받을 수 있나요?**
네. 다운로드는 모든 역할이 할 수 있고, 누가 받았는지 감사 로그에 남습니다.

**Q. 퇴근하면서 로그아웃만 하면 되나요?**
로그아웃해도 서명 키는 해제된 채 남습니다. 키를 해제했다면 **지금 봉인**도 누릅니다.

**Q. 사이트를 한글로 입력했는데 파일 이름에 한글이 없습니다. 다시 발급해야 하나요?**
아니요. 파일 이름만 영문·숫자로 바뀐 것이고, 파일 안의 사이트 ID는 한글 그대로입니다(§5.5). 이름은 마음대로 바꿔도 되며, 서명에는 영향이 없습니다.

**Q. 라이선스 파일의 시각이 화면과 9시간 다릅니다.**
파일은 UTC, 화면은 KST입니다. 예를 들어 KST 2026-11-01 00:00:00은 파일에 `2026-10-31T15:00:00Z`로 들어갑니다.
