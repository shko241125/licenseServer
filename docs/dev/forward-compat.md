# 라이선스 전방 호환 검토 (2026-10-19)

- **상태:** 검토 완료, 사용자 결정 대기(§10). 구현하지 않았습니다.
- **대상:** 이미 배포된 SDK(빌드할 때 고정된 정적 라이브러리)가 **나중에 형식이 바뀌어 발행된 라이선스**를 받을 수 있는가(전방 호환). 반대 방향(새 SDK가 이전 라이선스를 받음)은 §5.4.
- **목표(사용자):** 운영 중 라이선스를 다시 발행할 때 SDK를 다시 빌드하지 않는다.
- 근거: 코어 2.0.2 코드와 실측(§3.2). 문서 안의 오류 코드는 `1000 + Error 순번`입니다.

## 1. 결론

1. **지금 그대로 버전(`license_ver`)을 올리면 이전 SDK와 호환되지 않습니다.**
   - `full` 모드와 Manager는 항상 `1006`으로 거부합니다.
   - `signature` 모드는 버전을 보지 않습니다. 그래서 비호환 형식도 통과하고, SDK가 v1 의미로 **잘못 해석합니다.**
2. **추가형 변경은 지금도 호환됩니다.** 버전을 유지하고 선택 필드만 더하는 변경입니다. 발급 서버 UI를 추가형으로 진화시키면 추가 발행분도 이전 SDK의 `full`로 쓸 수 있습니다(§5).
3. 추가형으로 안 되는 변경에 대비해 서명된 체크 옵션 `check_mode`(`full`/`minimal`)를 형식에 넣고, **검사 수준을 라이선스가 정하게** 합니다(§6). 이렇게 하면 SDK는 추가 검사 없이 라이브러리 결과로 사용 여부를 정합니다.
4. 이 해석 규칙은 **SDK에 처음 들어가는 코어에 있어야만** 효과가 있습니다. 지금은 SDK 실제 적용 전이므로 코어 2.1.0으로 넣을 수 있습니다.
5. 재빌드 없이 바꿀 수 있는 범위는 **안정 필드**(§6.2)를 지키는 변경뿐입니다. 안정 필드의 경로·타입·의미가 바뀌면 어떤 방법으로도 SDK를 다시 빌드해야 합니다. 새 제한 필드는 이전 SDK가 집행하지 못합니다.

## 2. 전제: 정적 라이브러리에서 고정되는 것

- `stt_license`·`stt_license_key`는 정적 라이브러리입니다(`CMakeLists.txt`). 판정 규칙과 공개키가 SDK의 `.so` 안에 빌드할 때 고정됩니다.
- **SDK가 값을 읽는 코드도 같이 고정됩니다.** 예를 들어 `GetInt("allowed_channels.offline.sonastt")`의 경로, 타입, 의미가 그렇습니다.
- 현장의 검증 규칙은 그 SDK를 빌드할 때의 코어 버전입니다. 사이트마다 다를 수 있습니다.
- 모든 버전에서 바꿀 수 없는 것(공통 불변): 서명 키, Ed25519, RFC 8785 정규화, JSON 문법(`docs/sdk/04-license-format.md` §3), 64 KiB.

## 3. 현재 동작 (코어 2.0.2)

### 3.1 판정 경로
- **`full` 계열:** `full` 모드, Manager(`Open`·다시 읽기), `licensectl verify`(발급 서버 검증 화면)는 모두 같은 함수를 거칩니다.
  - 순서: `ParseAndVerify` → `VerifyTree`(문법·서명) → `ExtractFields`(표준 필드)
  - `ExtractFields`는 버전을 먼저 봅니다. 1이 아니면 `1006`입니다. 그다음 v1 필수 필드를 꺼냅니다.
  - 표에 없는 최상위·`validity` 키는 무시합니다. `allowed_channels`의 `total`이 아닌 키는 모두 항목 객체로 해석합니다.
- **`signature` 모드:** `VerifyTree`까지만 갑니다. 버전과 필드는 보지 않습니다.
- **발급(`SignContract`):** 같은 `ExtractFields`로 자기 검증을 합니다. 그래서 발급기는 자기 코어가 아는 형식만 발급할 수 있습니다.

임시 키로 직접 서명했고, 판정 시각은 2026-10-19입니다.

### 3.4 운영 중 결과
- **JNI `connect`:** 판정에 실패하면 SDK 초기화가 실패하고 STT 서버가 뜨지 않습니다.
- **Manager:** 다시 읽기에 실패해도 **기존 라이선스를 유지**합니다(`last_reload_error`에 코드가 남음). 그러나 기존 라이선스가 만료되면 멈추고, 다음 재시작 때는 기동하지 못합니다. 갱신하려고 바꾼 파일이면 장애가 **만료일에 늦게** 드러납니다.

## 4. 검토 중 발견한 문제

| 문제 | 내용 | 해결(§6) |
|---|---|---|
| `signature` 모드의 조용한 오해석 | 버전을 보지 않으므로 비호환 형식도 통과합니다. 운영 기본값이 `signature`라 영향 범위가 가장 넓습니다 | 연결 허용 판단을 `check_mode` 판정으로 통일 |
| 설정으로 검사를 끌 수 있음 | 검증 모드는 고객 현장의 SDK 설정 파일(`--license-verify-mode`)에서 읽고, 없으면 `signature`입니다(D15). D43의 "`trial`·`dev` 서버는 `full`"을 설정 한 줄로 끌 수 있습니다. 끄면 라이브러리는 만료를 보지 않습니다 | 검사 수준을 서명된 라이선스가 정하고, 설정으로 낮출 수 없게 |

## 5. 전략 1: 추가형 진화 (우선 적용)

### 5.1 규칙
버전을 올리지 않고 선택 필드만 더하면 이전 SDK의 `full`이 그대로 통과합니다. SDK를 다시 빌드할 필요가 없습니다.

| # | 규칙 | 어기면 이전 SDK의 `full` 결과 |
|---|---|---|
| A1 | 새 값은 최상위, `validity` 안, 또는 새 최상위 객체에 둡니다 | — |
| A2 | `allowed_channels`에는 항목 객체만 둡니다 | `1005` |
| A3 | v1 필수 필드의 타입·범위·의미를 바꾸지 않습니다 | `1005`, 또는 오류 없이 잘못 해석 |
| A4 | `license_ver`는 1로 유지합니다 | `1006` |
| A5 | 공통 불변(§2)을 지킵니다 | `1003` / `1002` / `1004` |
| A6 | 새 입력칸을 비우면 키를 아예 넣지 않습니다. 그래서 칸을 다 비우면 지금 v1과 같은 모양이 나옵니다 | — |
| A7 | 새 필드를 쓸 때는 항상 값을 명시합니다. 버전마다 다른 기본값을 두지 않습니다 | — |
| A8 | 새 **제한** 필드에는 "SDK 코어 x.y 이상에서만 적용"이라고 표시합니다 | 조용히 집행되지 않음 |

새 SDK는 새 필드가 **있으면 집행**하고 없으면 v1처럼 동작합니다. 필드의 존재 자체가 서명되므로 이것으로 충분합니다. 필드가 없는 파일은 그 제한 없이 정당하게 발급된 것입니다.

### 5.2 발급 쪽 변경 (새 필드마다)
- 코어 `SignContract`: 허용 키 목록과 필드 규칙. 발급 코어와 SDK 코어의 버전은 달라도 됩니다.
- 발급 서버:
  - `Contract.toJson`: 값이 있을 때만 키를 넣습니다.
  - 화면: `IssueForm`, `form.html`, `preview.html`, `detail.html`
  - 검증: `ContractValidator`와 코어 일치 시험
  - 갱신: `copyOf`
  - DB: NULL 허용 열을 추가하는 새 마이그레이션과 `license_guard()` 비교 목록
- **증명:** 이전 코어의 `licensectl verify`로 새 발급분을 검증하는 시험을 둡니다. 새 코어의 자기 검증만으로는 이전 SDK가 받는다는 증명이 되지 않습니다.

### 5.3 비추가형 변경일 때 이전 형식(v1)으로 발급하기
원리상 가능합니다. 이전 SDK는 파일 내용과 공개키만 봅니다. 그러나 **지금 코드로 되는 것은 아닙니다.** 코어 허용 키, `Contract.LICENSE_VER`, 폼, 검증, 장부, DB `CHECK (license_ver = 1)`이 모두 v1에 고정되어 있습니다. 버전을 올리는 작업을 할 때 다음을 요구사항으로 넣어야 합니다.
- 같은 서명 키를 씁니다.
- 형식별 허용 키와 판정을 둡니다. v1 판정 코드는 고치지 않고 그대로 둡니다.
- 이전 코어로 검증하는 시험을 둡니다.
- 발급 서버는 사이트별 지원 형식을 기록하고, 폼에서 형식을 고르게 합니다. 폼, 검증, DB 제약도 형식별로 둡니다.

이 비용은 D37(이전 형식 공존)에서 한 번 들였다가 D42에서 걷어낸 것과 같은 종류입니다.

### 5.4 새 SDK가 이전 라이선스를 받는 방향
새 코어는 `license_ver` 1을 **영구히** 받아야 합니다. 운영 라이선스는 영구(9999년)라서 현장에 계속 남기 때문입니다. D42("이전 형식 지원 제거")는 SDK 적용 전 형식에 대한 결정이며, 적용 이후의 v1에는 해당하지 않습니다.

## 6. 전략 2: 체크 옵션 `check_mode` (비상구)

### 6.1 값
| 값 | 라이브러리 판정 | 쓰는 때 |
|---|---|---|
| 없음 또는 `"full"` | 현행 `full`: 버전 1, v1 전체 필드, 기간 | 처음 발급분. 추가형 발급분 |
| `"minimal"` | 서명 + 안정 필드 + 기간. 버전과 나머지 필드는 보지 않음 | 추가형으로 안 되는 변경을 한 추가 발행분(안정 필드 유지가 발급 조건) |
| 그 밖의 값 | `1006` | 미래의 다른 수준에 대비해 실패 폐쇄 |

- 추가 발행분을 순수 `signature`로 검사하지 않는 이유가 있습니다. 순수 `signature`면 기간과 채널을 라이브러리가 보지 않아, 만료와 동시 세션 제한을 SDK가 따로 구현해야 하기 때문입니다(D17의 별도 만료 장치 문제가 그대로 남음).
- `minimal`은 집행 강도가 `full`과 같습니다.

### 6.2 안정 필드 (영구 고정, SDK 첫 적용 전에 확정)
| 경로 | 규칙(현행 v1과 같음) |
|---|---|
| `check_mode` | §6.1 |
| `license_id` | 문자열 1~128바이트. 장부 조회와 현장 문의용 |
| `allowed_channels.total` | 정수 1~100000 |
| `allowed_channels.<항목>.<세부 항목>` | `total`이 아닌 키는 모두 항목 객체. 값은 정수 0~`total`, 항목과 세부 항목 각 64개 이하, 1 이상인 값이 하나 이상 |
| `validity.not_before`, `validity.not_after` | `YYYY-MM-DDTHH:MM:SSZ`, `not_before < not_after`, 종료 시각 포함 |

- `license_type`을 넣을지는 결정 대기입니다. SDK가 유형에 따라 동작을 나눈다면 넣어야 합니다.
- **SDK가 동작 판단에 쓰는 필드가 곧 안정 필드입니다.**

### 6.3 우선순위
- 검사 수준은 **라이선스가 정합니다.** `Verify(text, mode, …)`의 `mode` 인자로 낮출 수 없습니다.
- 설정 `--license-verify-mode`는 폐지합니다(D15·D17 대체).
- `VerifySignature`는 SDK가 값을 직접 읽는 용도로만 남기고, 연결 허용 판단에는 쓰지 않습니다.

### 6.4 `minimal` 판정 순서
실패하면 그 단계에서 멈춥니다.

| 단계 | 검사 | 실패 코드 |
|---|---|---|
| 0 | 64 KiB, 문법, `signature` 형식, Ed25519 | `1002` / `1003` / `1004` |
| 1 | `check_mode`: 문자열 `"full"`·`"minimal"`만 | 다른 문자열이면 `1006`, 문자열이 아니면 `1005` |
| 2 | `license_id` | `1005` |
| 3 | `allowed_channels` | `1005` |
| 4 | `validity` 형식과 순서 | `1005` |
| 5 | 현재 시각 기준 기간 | `1007` / `1008` |
| — | `license_ver`, `project_name`, `license_type`(안정 필드로 정하면 2단계에 추가), `solution`, `site_id`, `warning_notice`, `issued_at`, 모르는 키 | 검사하지 않음. 표시 필드는 규칙에 맞으면 채우고 아니면 빈 값 |

Manager는 운영 중에 채널을 잡을 때마다(`Acquire`) 다음을 다시 봅니다.
- 기간이 지났거나 시작 전이면 `1008` / `1007`
- 라이선스에 없거나 상한이 0인 엔진은 `1011`
- 세부 항목이나 `total`이 모두 쓰이는 중이면 `1009`

### 6.5 SDK가 할 일
- **결과 코드만 보고 연결 여부를 정합니다.** 로그에는 `ErrorName`, `detail`, `fields.check_mode`를 남깁니다. `check_mode`는 원문이 아니라 라이브러리가 돌려준 `fields.check_mode`를 봅니다.
- **값 적용(집행):**
  - 세션 풀 크기는 `min(설정값, 세부 항목 상한)`입니다.
  - 동시 예약은 세부 항목 상한과 `total`을 둘 다 지킵니다.
  - 라이선스에 없는 엔진은 상한 0으로 봅니다.
  - Manager를 쓰면 라이브러리가 대신 합니다.
- **운영 중 기간 재판정:** JNI `connect` 방식은 연결할 때 한 번만 판정합니다(기존 미결 "갱신 방식"). Manager는 60초마다 다시 판정합니다.
- **표시 필드:** `minimal`에서는 빈 값일 수 있으므로 화면과 로그에서 처리합니다.
- **하지 말 일:**
  - 범위나 기간을 다시 검사하지 않습니다.
  - 안정 필드가 아닌 값으로 동작을 정하지 않습니다.
  - 원문 JSON을 직접 해석해 판단하지 않습니다.
  - SDK 자체 검사는 기존 `.key` 경로(라이브러리가 `ParseError`를 낼 때)에만 씁니다.

### 6.6 보안
| 위협 | 결과 |
|---|---|
| 고객이 `full` 파일을 `minimal`로 고침 | `1004` |
| 고객이 설정으로 검사 수준을 낮춤 | 불가(라이선스가 정함). 현행보다 강해집니다 |
| `minimal` 파일로 만료·채널을 우회 | 불가. `minimal`에서도 기간과 채널을 집행합니다 |
| 다른 사이트의 파일을 재사용 | 현행 복제 문제(D24)와 같아 변화 없음 |
| 발급자가 안정 필드의 의미를 바꾼 파일을 `minimal`로 발행 | 이전 SDK가 잘못 해석합니다. 발급 단계의 자기 검사와 이전 코어 시험으로만 막을 수 있습니다 |

## 7. 예시 (`check_mode: "minimal"`, 판정 시각 2026-10-19)

```json
{
  "check_mode": "minimal",
  "license_ver": 3,
  "license_id": "9b1c...",
  "allowed_channels": { "total": 16, "offline": { "sonastt": 8 }, "online": { "sonastt": 8 } },
  "validity": { "not_before": "2026-10-01T00:00:00Z", "not_after": "2027-09-30T14:59:59Z" },
  "host_binding": "srv-a",
  "signature": "..."
}
```

| # | 상황 | 결과 |
|---|---|---|
| M1 | 위 예시 그대로 | Ok. 이전 SDK는 `host_binding`을 **집행하지 않음** |
| M2 | `project_name`·`solution`·`site_id`·`warning_notice` 없음 | Ok, 표시 필드는 빈 값 |
| M3 | `site_id: 123`(정수) | Ok, 빈 값 |
| M4 | `check_mode: "Minimal"`(대문자) | `1006` |
| M5 | 고객이 `full` 파일의 `check_mode`를 `minimal`로 고침 | `1004` |
| M6 | `license_id` 없음 | `1005` |
| M7 | `total: 200000` | `1005`(안정 필드 범위는 늘릴 수 없음) |
| M8 | `total: 16`인데 `offline.sonastt: 20` | `1005` |
| M9 | `allowed_channels.burst: 2` | `1005` |
| M10 | 모든 세부 항목이 0 | `1005` |
| M11 | `not_after`가 `"2027-01-01"`, `"…T00:00:00.000Z"`, `"…+09:00"` 형식 | `1005` |
| M12 | `not_before ≥ not_after` | `1005` |
| M13 | `not_before` 2026-11-01 | `1007` |
| M14 | `not_after` 2026-10-18T23:59:59Z | `1008` |
| M15 | 새 필드에 배열 | `1003`(`.key` 분기를 켰으면 기존 해독기로 넘어가지만 거기서도 거부) |
| M16 | 70 KiB | `1002` |
| M17 | 다른 키로 서명 | `1004` |
| M18 | 운영 중 라이선스에 없는 `online.sonaml` 요청 | `1011`(재시도해도 같음) |
| M19 | 운영 중 `offline.sonastt` 8개 사용 중, 또는 `total` 소진 | `1009`(잠시 뒤 재시도) |
| M20 | 운영 중 `not_after` 경과 | Manager는 다음 점검 때 `1008`. JNI `connect`만 쓰면 재시작 전까지 모름 |

`minimal`이 거부하는 사유는 서명·채널·기간뿐이라 `full`과 같은 종류입니다. 조용히 통과하는 것은 새 제한 필드(M1)와 표시 필드 누락(M2·M3) 두 가지입니다.

## 8. 검토 후 버린 안

| 안 | 버린 이유 |
|---|---|
| `compat_ver`(정수, "v1 전체 규칙을 지킴" 선언) | 사용자 의도(표시 필드 변경까지 허용)보다 범위가 좁습니다. 같은 문제를 두 장치로 풀 필요가 없습니다 |
| 추가 발행분은 순수 `signature` | 라이브러리가 기간과 채널을 보지 않습니다(§6.1) |
| 설정이 라이선스보다 우선 | 설정으로 검사를 낮추는 우회가 남습니다(§4) |
| `check_mode`에 `full`만 정의 | "SDK는 항상 `full`"과 효과가 같아 의미가 없습니다 |
| 버전과 무관하게 v1 필드만 보고 통과 | 의미가 바뀐 형식도 통과해 실패 폐쇄를 잃습니다 |
| 키 단위 `critical` 목록 | 문법에 배열이 없고, 필요한 것보다 표현력이 큽니다 |

대안(안 가): 추가형으로 안 되는 변경은 하지 않겠다고 확정할 수 있다면, `check_mode` 없이 "SDK는 항상 `full`, 설정 폐지"가 가장 단순합니다. 이때 비추가형 변경은 SDK 재빌드나 v1 하위 발급(§5.3)으로 처리합니다.

## 9. 구현 범위 (권고안, 코어 2.1.0)

| 대상 | 변경 |
|---|---|
| `core/src/license.cpp` | `ExtractFields`에서 `check_mode`를 먼저 판정(`full`은 현행 코드 그대로, `minimal` 분기 추가, 그 밖은 `1006`). `Verify`는 `mode` 인자로 수준을 낮추지 않음 |
| `license.h`, `detail.h` | `LicenseFields`·`LicenseData`에 `check_mode` 추가. `VerifyMode`와 `UnsupportedVersion` 주석 |
| `licensectl verify` | 적용된 검사 수준 출력(`-json`에 `check_mode`) |
| 발급(`SignContract`), 발급 서버 | 이번에는 변경 없음(`check_mode`를 생략하면 `full`). `minimal` 발급은 실제로 필요해질 때 자기 검사와 함께 엽니다 |
| `Error` 순번, 골든 파일 | 변경 없음 |
| SDK 문서 | 02 §4·§5(설정 모드 폐지, `fields.check_mode`), 04 §2·§5(체크 모드, 안정 필드, 추가형 규칙 A1~A8), 05 수용 기준, 06 현장 조치(교체 전에 같은 코어 버전으로 사전 점검) |
| 결정 기록 | D45 신설, D15·D17·D43④에 "대체됨" 표시 |

시험:
- `full`: 기존 시험 전부. `check_mode: "full"`을 명시한 파일도 같은 결과
- `minimal`: §7의 M1~M17(`SignRaw`로 생성, 키는 매번 새로)
- 설정 우회: `Verify(SignatureOnly)`로 만료된 `full` 파일을 넣으면 `1008`
- Manager: `full` 파일을 `minimal` 파일로 교체해 다시 읽기, M18~M20
- 그 밖: JNI 하네스, 퍼저 시드, 서버 단위·통합 테스트 재실행(새 `licensectl`)

## 10. 결정이 필요한 것

1. 방향: 추가형 진화 + `check_mode`(권고) 또는 안 가(`check_mode` 없음, SDK 항상 `full`, 설정 폐지)
2. 우선순위: 라이선스가 검사 수준을 정함(권고, D15 대체)
3. 안정 필드 목록 확정. 특히 `license_type` 포함 여부. **SDK 첫 적용 뒤에는 바꿀 수 없습니다**
4. 이름: `check_mode`, `full`/`minimal`
5. 일정: SDK 첫 적용 착수 전에 코어 2.1.0 전달. SDK 팀이 2.0.2로 적용을 시작했는지 확인 필요
