# `check_mode` 안내: 언제 쓰고, 어떻게 발급하고, 어디에 표시하나

- **작성:** 2026-10-23
- **대상:** 발급 담당, 발급 서버 개발자, SDK 적용 담당
- **이 문서의 역할:** 흩어진 결정과 설계를 사례별로 정리한 길잡이입니다. 규칙의 원본은 아래 문서이고, 서로 다르면 원본이 맞습니다.
  - 형식 규칙: [../sdk/04-license-format.md](../sdk/04-license-format.md) §2·§5
  - 결정: [DECISIONS.md](DECISIONS.md) D46·D47
  - 설계 전체: [forward-compat.md](forward-compat.md) §7(판정), §8(예시), §13(발급 서버)
- **한 줄 요약:** 지금(판 1)은 `check_mode`를 쓰지 않습니다. 파일에 키가 없는 것이 정상이고, 없으면 `full`입니다. `"minimal"`은 `license_ver` 2가 생긴 뒤, 그 판을 모르는 SDK가 현장에 있을 때만 서버가 규칙에 따라 넣습니다.

## 1. 먼저 알아 둘 세 가지

### 1.1 "안정 필드(영구 고정)"는 "필수"가 아닙니다
| 축 | 뜻 | `check_mode` |
|---|---|---|
| 안정(영구 고정) | 키의 경로·타입·의미를 어떤 판에서도 바꾸지 않음 | 예 |
| 필수 | 파일에 반드시 있어야 함 | **아니오.** 없으면 `full` |

안정 필드는 `check_mode`, `license_id`, `allowed_channels`, `validity.not_before`·`not_after`입니다. 이 중 `check_mode`만 생략할 수 있고, 나머지는 필수입니다. "없음 = `full`"이라는 뜻도 영구히 고정됩니다.

### 1.2 파일에 적힌 값과 판정 결과의 값은 다릅니다
| 어디에 | 무엇 | 지금 값 |
|---|---|---|
| 라이선스 파일의 `check_mode` 키 | 이 판을 **모르는** 검증기에게 주는 지시 | 없음 |
| 판정 결과의 `check_mode`(SDK `fields.check_mode`, `licensectl verify`, 발급 서버 검증 화면) | 검증기가 **실제로 적용한** 수준 | 항상 `full` |

그래서 파일에 키가 없어도 검증 결과에는 `full`이 나옵니다. 판정 결과가 `minimal`이면 "이 SDK는 이 형식 판을 모른다(업그레이드 대상)"는 뜻입니다.

### 1.3 `check_mode`는 "모르는 판"일 때만 효과가 있습니다
| 파일 | 그 판을 **아는** 코어 | 그 판을 **모르는** 코어 |
|---|---|---|
| 키 없음(= `full`) | 그 판의 전체 규칙 | `1006` 거부(실패 폐쇄) |
| `"minimal"` | 그 판의 전체 규칙(키 없음과 같음) | 서명 + 안정 필드 + 기간만 보고 받음 |
| `"full"` 명시 | 키 없음과 같음 | 키 없음과 같음 |
| 그 밖의 문자열(대소문자 다름 포함) | `1006` | `1006` |
| 문자열이 아님 | `1005` | `1005` |

- "아는 판"은 SDK에 빌드된 코어가 정합니다. 코어 3.0.0이 아는 판은 1뿐입니다(`MaxLicenseVer()` = 1). 파일이나 설정으로는 바뀌지 않습니다.
- `minimal`도 집행은 약해지지 않습니다. 서명, 채널 상한(`total`·세부 항목), 기간을 똑같이 막습니다. 판정하지 않는 것은 표시용 필드(`project_name`, `license_type`, `solution`, `site_id`, `warning_notice`, `license_ver`, `issued_at`)뿐이며, 이 값들은 비어 있을 수 있습니다.

## 2. 사례별 정리: 무엇을 발급하나

기준은 **그 사이트의 STT 서버들에 들어간 SDK 코어가 아는 판**입니다. 파일 한 장이 한 사이트에 가기 때문입니다.

| # | 상황 | 발급할 파일 | 현장 SDK 판정 | 판정 결과 `check_mode` | 비고 |
|---|---|---|---|---|---|
| A | **지금.** 형식은 판 1뿐(필드를 더하는 추가형 변경 포함) | 판 1, 키 없음 | 판 1 전체 규칙 | `full` | 발급 유형(운영·시험·개발)과 무관 |
| B | 판 2가 있고, 그 사이트의 모든 SDK가 판 2를 앎 | 판 2, 키 없음 | 판 2 전체 규칙 | `full` | |
| C | 판 2를 그 사이트 SDK(예: 3.0.0)가 모르고, 판 2가 안정 필드를 지킴 | 판 2 + `"minimal"`, 또는 하위 판 1 | 서명·안정 필드·기간만 | `minimal` | 판 2의 새 필드는 그 SDK에서 집행되지 않음 |
| D | 한 사이트에서 SDK를 차례로 교체하는 중이고, 한 파일을 함께 씀 | 판 2 + `"minimal"` | 옛 SDK는 최소 판정, 새 SDK는 판 2 전체 규칙 | 옛 SDK `minimal`, 새 SDK `full` | **`minimal`이 꼭 필요한 경우** |
| E | 판 2가 안정 필드를 바꿈(채널 구조, 기간 형식 등) | 하위 판(SDK가 아는 판) | — | — | `minimal`로도 받지 못함. 아니면 SDK 재빌드 |
| F | 옛 SDK에서도 표시 필드가 정확히 보여야 함 | 하위 판 | — | — | `minimal`이면 표시 필드가 빈 값일 수 있음 |
| G | 사이트 SDK 코어 기록이 없음(모름) 또는 업그레이드 예정 | 판 2 + `"minimal"` | 사이트 SDK에 따라 C 또는 B | — | 결정 D47 D3 안 C의 "모름·혼재·업그레이드 예정" |

**발급하지 않는 파일**
- `"full"`을 명시한 파일: 키가 없는 파일과 같으므로 넣지 않습니다.
- 판 1 + `"minimal"`: 판 1은 모든 코어가 알아서 전체 규칙으로 판정하므로 의미가 없습니다. 지금 발급 도구는 이 키를 아예 거부합니다.

**잘못 판단했을 때**
- B로 보고 키 없이 냈는데 실제로는 옛 SDK가 있으면: `1006`으로 거부됩니다.
  - JNI `connect` 방식이면 STT 서버가 뜨지 않습니다.
  - Manager 방식이면 기존 파일을 유지하다가 그 파일이 만료될 때 멈춥니다.
  - 바로 드러나는 실패라 안전한 쪽입니다(실패 폐쇄).
- C·D·G로 `minimal`을 냈는데 실제로는 모든 SDK가 판 2를 알면: 결과는 키 없음과 같습니다. 손해가 없습니다.

## 3. 발급 서버에서 어떻게 적용하나

### 3.1 지금(서버 1.8.0, 코어 3.0.0)
- 발급 화면에 `check_mode`를 고르는 칸이 없습니다. 판 1뿐이라 필요 없습니다.
- 파일에 키가 들어가지 않도록 두 겹으로 막혀 있습니다.
  1. 서버 `Contract.toJson`이 이 키를 만들지 않습니다.
  2. 발급 도구(`SignContract`, `licensectl issue`·`sign`)가 판 1 허용 키만 받습니다. 계약에 넣으면 `LICENSE_INVALID_FIELD: check_mode: unknown key (not in license_ver 1)`로 거부합니다.
- 시험: `IssueFlowIT`(발급 파일의 키 목록이 정확히 판 1 키 + `signature`), `scripts/check.sh` 3단계, 코어 `CheckMode.IssuerRejectsCheckModeInContract`.

### 3.2 판 2를 만들 때(설계, 아직 구현 전)
원칙은 **사람은 형식 판만 고르고, `check_mode`는 서버가 규칙으로 정한다**입니다(forward-compat §13.3 I3·I4).

| 계층 | 할 일 | 근거 |
|---|---|---|
| 발급 폼 | "형식 판" 선택 칸. 판이 둘 이상일 때만 보임. 기본값은 갱신이면 원본 판, 새 발급이면 그 사이트의 마지막 판, 사이트 이력이 없으면 최신 판. 판에 없는 입력 칸은 숨김 | §13.4 |
| `check_mode` 결정 | 사이트별 SDK 코어 기록을 보고 §2 표대로: 모두 알면 키 없음, 아니면 `"minimal"` | D47 D3 |
| 자기 검증 | 발급 직후 (a) 판 2 전체 규칙 (b) 3.0.0의 최소 판정(`ExtractMinimal` 직접 호출)을 모두 통과 | I5 |
| 최저 코어 판정 | 서버 이미지에 SDK에 나간 코어의 `licensectl`을 넣고, 발급 파일이 그 코어에서 `result == "OK"`여야 발급 완료 | I8 |
| 갱신 | 원본의 판을 그대로 씀. 판을 바꾸면 경고 | I7 |
| 판 1 코드 | 고치지 않음(`SignContract` 판 1 규칙, `Contract.toJson`, `ContractValidator`) | I6 |
| DB | 새 마이그레이션으로 `check_mode` 열(NULL 허용)과 제약 `check_mode IS NULL OR (license_ver >= 2 AND check_mode = 'minimal')`. V1~V6은 고치지 않음 | §13.4 |

판 2 전에 정할 것(forward-compat §13.6):
1. 사이트별 SDK 코어 기록 방식: 발급 화면에서 고르기 / 사이트 장부(`site_id` → SDK 코어 버전)
2. 최저 코어 판정에 쓸 코어 목록: 최저 코어만 / SDK에 나간 모든 코어
3. 판 2의 첫 내용. 안정 필드를 바꾸면 `minimal`로 전방 호환이 되지 않습니다(사례 E)

## 4. 어디에 어떻게 표시하나

| 위치 | 지금 | 판 2 이후(설계) |
|---|---|---|
| 발급 폼 | 없음 | 형식 판 선택 |
| 미리보기 | 없음 | 판과 서버가 정한 `check_mode`. `minimal`이면 "이 사이트의 옛 SDK는 최소 판정, 새 필드는 그 SDK에서 집행되지 않음" 안내 |
| 상세·목록 | 없음(파일·DB에 없는 값) | 판, `check_mode`, 최저 코어 판정 결과 |
| 검증 화면 | `license_ver`, `check_mode`(적용한 수준, 지금은 늘 `full`) | 서버 최신 코어 판정 + "SDK 최저 코어 판정" 결과를 함께 |
| `licensectl verify` | `check_mode : full`, `-json`의 `check_mode` | 같음. `minimal` 적용이면 `issued_at` 빈 문자열 가능 |
| 현장 SDK 로그 | `check_mode=full lib=3.0.0 max_ver=1` | 사례 C·D의 옛 SDK는 `check_mode=minimal` → 업그레이드 대상 |

SDK 쪽 표시 규칙
- 로그에는 원문 JSON이 아니라 라이브러리가 돌려준 `CheckModeName(fields.check_mode)`, `LibraryVersion()`, `MaxLicenseVer()`를 남깁니다.
- 동작 판단에는 안정 필드만 씁니다(`fields.total_channels`, `fields.channels`, 기간은 라이브러리가 판정). `license_type`·`license_ver`로 동작을 나누면 `minimal` 파일에서 깨집니다.
- 표시 필드는 `minimal`에서 빈 값일 수 있으므로, 화면·로그가 빈 값에도 오류 없이 동작해야 합니다(SDK 수용 기준 05-testing §3).

## 5. 자주 묻는 질문

| 질문 | 답 |
|---|---|
| 기본은 `full`인가? | 예. 키가 없거나 `"full"`이면 `full`입니다. 아는 판이면 `"minimal"`이 있어도 전체 규칙입니다 |
| `license_ver` 2부터 표시되나? | 아닙니다. 판정 결과의 `check_mode`는 판 1에서도 항상 나옵니다(지금은 `full`). 파일 키로 들어가는 것만 판 2부터입니다 |
| production 발급부터 표시되나? | 아닙니다. 발급 유형과 무관합니다. 운영·시험 모두 파일에 키가 없고 판정은 `full`입니다(2026-10-23 실측) |
| 다운로드한 `.lic`에 `check_mode`가 없다. 문제인가? | 정상입니다 |
| 고객이 파일의 `check_mode`를 고치면? | 서명 대상이라 `1004`입니다 |
| SDK 설정으로 `minimal`을 강제할 수 있나? | 없습니다. 검사 수준은 라이선스가 정합니다(D46 ④) |
| 이전보다 높은 판이 아니면 `full`로 다시 발급해도 되나? | 됩니다. 기준은 "그 사이트 SDK가 아는 판"입니다. 이전 파일이 키 없이 받아들여졌다면 그 판을 안다는 증거입니다. 이전 파일이 `minimal`이었다면 증거가 되지 않습니다 |
| 판 1 안에서 필드를 더하면 `minimal`이 필요한가? | 아닙니다. 추가형 변경은 옛 SDK가 `full`로 받습니다. 다만 새 **제한** 필드는 그것을 아는 코어에서만 집행됩니다 |

## 6. 판 2를 시작할 때 점검표
- [ ] 판 2의 변경이 안정 필드를 지키는가(지키지 않으면 사례 E: 하위 판 또는 SDK 재빌드)
- [ ] 사이트별 SDK 코어 기록 방식을 정했는가(§3.2 미결 1)
- [ ] DECISIONS에 판 2 결정을 추가했는가
- [ ] 코어: 아는 판 목록에 2를 더하고 판 1 판정 코드는 그대로인가, `ExtractMinimal`을 고치지 않았는가
- [ ] 서버: 폼·미리보기·상세·목록·검증 화면 표시(§4), DB 마이그레이션, 자기 검증 I5, 최저 코어 판정 I8
- [ ] 시험: 3.0.0 `licensectl`로 판 2 + `minimal` 파일이 `OK`·`check_mode: minimal`, 판 2 키 없음 파일이 `1006`
- [ ] 문서: 04-license-format §5, 이 문서, 두 매뉴얼(서버 사용자 매뉴얼 §6.3, SDK 개발자 매뉴얼 §4.4)
