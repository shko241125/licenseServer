# 06. 현장 설치·운영

라이선스 **발급**은 사내 발급 서버가 합니다. 이 문서는 받은 `license.lic`를 고객 현장에 설치하고 문제를 처리하는 절차입니다.

## 1. 반입 전 확인 (사내, 필수)

```bash
licensectl verify -pub public.key license.lic                             # 지금 시각 기준
licensectl verify -pub public.key -at 2027-09-25T00:00:00Z license.lic    # 특정 시각(설치 예정일 등) 기준
```
- 종료 코드: 서명이 맞고 상태가 `VALID`이면 0, 그 밖에는 1입니다.
- `public.key`는 **해당 제품 빌드에 내장된 운영 공개키**여야 합니다. 발급 서버 화면의 검증 기능을 써도 됩니다.

## 2. 설치 (고객 폐쇄망)

1. 보안 USB나 망간 반입 결재로 `license.lic`를 전달합니다.
2. 호스트의 `/opt/app/license/license.lic`에 둡니다. 컨테이너에는 디렉터리 단위로 읽기 전용 마운트됩니다(03-stt-server.md §4).
3. 파일을 **열어서 저장하지 않습니다.** 공백·줄바꿈은 서명에 영향이 없지만, 편집기의 인코딩 변환이나 실수로 인한 한 글자 변경은 `1003`/`1004`가 됩니다.
4. 컨테이너를 기동합니다. 라이선스가 거부되면 서버가 기동하지 않고 종료되며, 로그에 오류 이름이 남습니다.
5. 설치 확인서에 호스트명, 인스턴스 수, `license_id`를 기록합니다.

**갱신:** 현재는 파일을 교체한 뒤 **컨테이너를 재시작**합니다(갱신 방식은 미정, 02-integration.md §8). `docker kill -s HUP`은 쓰지 않습니다(JVM 종료).

## 3. 오류별 조치

| 코드 | 이름 | 의미 | 조치 |
|---|---|---|---|
| 1001 | `LICENSE_FILE_NOT_FOUND` | 파일 없음·읽기 권한 없음 | 마운트 경로, `LICENSE_FILE_PATH`, 파일 권한 확인 |
| 1002 | `LICENSE_FILE_TOO_LARGE` | 64 KiB 초과 | 경로가 다른 파일을 가리키는지 확인, 원본 재배치 |
| 1003 | `LICENSE_PARSE_ERROR` | JSON 아님·형식 위반(편집 흔적, 기존 `.key`) | 원본 재배치. 기존 `.key`라면 새 형식 라이선스 요청 또는 공존 설정 확인 |
| 1004 | `LICENSE_BAD_SIGNATURE` | 내용 수정 또는 다른 키로 서명(개발용·타 제품) | 원본 재배치. 계속되면 발급처에 문의(제품 빌드와 발급 키 확인) |
| 1005 | `LICENSE_INVALID_FIELD` | 필드 규격 위반 | 발급처 재발급 |
| 1006 | `LICENSE_UNSUPPORTED_VERSION` | 엔진이 모르는 형식(더 새로운 `license_ver`이고 `check_mode`가 없음, 또는 모르는 `check_mode` 값) | 엔진 업그레이드 또는 이 엔진이 아는 형식의 라이선스 요청. 엔진이 아는 형식은 로그의 `library_version`·`max_license_ver`(02-integration.md §4)로 알려 줌 |
| 1007 | `LICENSE_NOT_YET_VALID` | 시작일 이전 | 호스트 시계(UTC) 확인. 시작일 전 설치라면 대기 |
| 1008 | `LICENSE_EXPIRED` | 종료 시각 지남(시험·개발. 운영은 영구) | 갱신본 설치 |
| 1009 | `LICENSE_CHANNEL_LIMIT` | 세부 항목(엔진) 상한 또는 전체(`total`) 채널 모두 사용 중 | 정상 동작. 지속되면 채널 증설 계약 |
| 1010 | `LICENSE_INTERNAL_ERROR` | 내장 공개키 손상 등 | 엔진 재설치, 개발사 문의 |
| 1011 | `LICENSE_ENGINE_NOT_LICENSED` | 라이선스에 없거나 상한 0인 항목·세부 항목 | 엔진 설정과 라이선스의 항목 이름(`licensectl verify`) 확인. 필요하면 해당 항목을 넣어 재발급 |

1007·1008은 모든 새 형식 라이선스에 대해 라이브러리가 판정합니다(코어 3.0.0부터 `signature` 모드 없음). 기존 `.key`의 기간 오류는 SDK의 별도 만료 장치가 출력하는 메시지를 따릅니다.

## 4. 알려진 한계 (계약·실사로 통제)

- **시계 조작**
  - 호스트 시계를 과거로 돌리면 기간 검사를 우회할 수 있습니다.
  - 시계는 그대로 두고 엔진 프로세스에만 가짜 시각을 보여 주는 방법(`LD_PRELOAD`로 시간 함수 가로채기)도 통합니다(실측 확인).
  - 실사 때는 컨테이너 환경변수(`LD_PRELOAD` 등)와 이미지 변경 여부를 확인합니다.
- **복제**
  - 같은 이미지와 파일을 다른 서버·사이트로 복사해 쓰는 것을 기술적으로 막지 않습니다.
  - 채널 수는 **인스턴스(프로세스)마다** 적용됩니다. 설치 확인서의 호스트명·인스턴스 수와 대조합니다.
- **바이너리 패치**: 검증 코드 자체를 패치하는 공격은 막지 않습니다. 심볼 은닉은 외부 라이브러리를 끼워 넣는 방식(`LD_PRELOAD`)만 막습니다.
- **공개키 교체**
  - 비밀키가 유출·분실되면 새 키쌍 → SDK 재빌드 → 전 고객 재배포·재발급이 필요합니다.
  - 이전 키로 서명된 라이선스는 새 엔진에서 모두 거부됩니다.
